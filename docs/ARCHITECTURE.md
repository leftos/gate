# gate — architecture

gate is a Cargo workspace whose `gate` binary (`gate.exe`) queues heavy commands onto a fixed number of CPU slots, watches them and kills runaway process trees. Its layers, bottom up: the shared state crates (`gate-state`, `proc-table`), the pure rule crates (`gate-watchdog`, `gate-args`, `gate-router`), the Win32 layer (`gate-win32`) and the binary that composes them.

The rule that shapes it: every file and kernel object another process sees is defined once, in `gate-state`, and the pure crates hold no Windows types, so they build and test on Linux. The design is [design.md](design.md); terms used in a project sense are in the [glossary](GLOSSARY.md).

`gate-state` and `proc-table` exist (moved in from ops-tower with their history, GATE-4), and so do `gate-args` and the `gate` binary's skeleton (GATE-32).

`gate-win32` exists with the named mutexes and events (GATE-33), and the `gate` binary has the slot loop (GATE-34, GATE-30), `gate stop-tree` (GATE-57) and the box side's `boot` and `preflight` verbs (GATE-59) and its `run` and `stop` verbs (GATE-60). `gate-watchdog` exists as a pure crate (GATE-56), and the `gate` binary uses it through `watch.rs` (GATE-58).

`gate-router` exists as a pure crate (GATE-66): the routing decision, `remote.json` parsing, the `-like` matcher, the path rewrite and the work-folder key. The `gate` binary asks it for the routing decision through `route.rs`.

## Layers

- **`proc-table`** (`crates/proc-table/`): owns the process snapshot model (`ProcessInfo`, `ProcessTable`, `ProcessTree` with its `descendants`) and its Windows reader. References `windows-sys` in its `win32` module only. Never depends on any gate crate: ops-tower and its other crates use it too.
- **`gate-state`** (`crates/gate-state/`): owns every file format in the state root, their readers and writers, the path and object-name rules, journal history and the dashboard state ops-tower shows. References `proc-table`. Never depends on `gate-win32`, `gate-watchdog`, `gate-router` or the binary, and its API exposes no `windows` or `windows-sys` types.

  It reads two layouts. `v1.rs` is `gate.exe`'s, under the state root (`counts_path`, `read_counts`). `counts.rs`, `claims.rs`, `remote.rs`, `state.rs` and `win32.rs` (`slot_count_path`, `live_inputs`, `dashboard_state`) are the PowerShell gate's, under `%LOCALAPPDATA%\gate\`, and only ops-tower uses them; the `gate` binary never does.

  `counts.rs` also writes the PowerShell layout's counts file for ops-tower's Gates tab (`apply_slot_count`, `write_slot_counts`). `apply_slot_count` keeps the other pool's valid count, replaces a missing, blank, invalid or non-object file, and fails with `ApplyError::Read` on a file that exists but cannot be read, leaving it untouched.
- **`gate-watchdog`** (`crates/gate-watchdog/`, pure): owns the free-share, load-adjusted clock, stall, ceiling and backstop arithmetic over samples (`share.rs`, `watch.rs`), the kill lines, the pure formatting of the diagnostics block a kill writes (`diagnostics.rs`: `lines`, `failed_block`, `failed_line` and the caps `JOB_LINES` and `OUTSIDE_LINES`), and the box heartbeat's beat rule and pump (`heartbeat.rs`). The cores-hint arithmetic is not built yet. References nothing of the gate's but plain data types. Never reads a clock, a process or a file itself: the clock, the samples and the CPU are injected.
- **`gate-args`** (`crates/gate-args/`, pure): owns the gate's own argv (the subcommand CLI and the compatibility layer), C-runtime and cmd.exe quoting, the `%VAR%` refusals and the PATHEXT resolution rules; the command's words are in `cmdline.rs` (C-runtime quoting, `command_text`), `batch.rs` (batch targets, cmd.exe quoting, refusals) and `program.rs` (program resolution). Never depends on `gate-win32`; the environment and file lookups it needs are injected.
- **`gate-router`** (`crates/gate-router/`, pure): owns the routing decision (`decide`, `Route`), `remote.json` parsing (`config.rs`), the `-like` matcher (`like.rs`), the in-worktree path rewrite (`rewrite.rs`), the `--no-build` drop and the work-folder key (`key.rs`), over strings.

  Reads no file, runs no git, ssh or process, and has no clock or environment: each fact comes through its `Facts` trait, asked only at the rule that needs it. Never depends on `gate-win32`, `windows-sys` or any other gate crate; its only dependencies are `serde_json` and `sha2`.
- **`gate-win32`** (`crates/gate-win32/`, Windows only).

  Built so far: named mutexes, events and process start times (the gate's own, and `process_start_of(pid)` for another process, `None` for a pid that is gone or exited).

  Also `device_target` (`device.rs`: the target of a drive letter's DOS device over `QueryDosDevice`, which the routing facts use to follow `subst` drives), `system_directory` (the folder holding cmd.exe), `runs_below_normal` (the gate's own priority class), `win32_message`, `boot_time` (when the machine booted), and job objects (`Job`: create, terminate, process ids, `accounting`; `OpenedJob`: open by name, process ids, terminate). Process stopping is `StoppableProcess` (open, created, wait, terminate; in `tree.rs`). `working_set(pid)` (`memory.rs`) is another process's working set in bytes, `None` for a pid that is gone or exited.

  Suspended process creation is `Launch` → `Suspended` → `Running`, with `EnvironmentBlock`, `same_variable_name` and `PriorityClass`. The box's piped launch is `PipedLaunch` → `PipedSuspended` (in `piped.rs`: a hidden console, breakaway from the caller's job, two pipes and a query-only job handle inherited), with `check_plain_file` and `breakaway_refused`. Both launches create the process through the shared `create.rs` (`check_launch`, `startup_info`, `AttributeList`, `create_process`, `create_inheriting`), so the refusals before the call and the startup information are one code path.

  The spawn lock (in `create.rs`) is held while the layer starts any process: `create_inheriting` makes inheritable copies of a launch's handles under it, so the gate's own handles are never inheritable, and `spawn(&mut Command)` starts a std `Command` under the same lock. A std spawn anywhere in the gate goes through `gate_win32::spawn`.

  Also the samples in `times.rs` (`system_times`, `process_times`, `file_time_now`) and the Ctrl+C handler in `interrupt.rs` (`Interrupt`: install, is_raised, raise; `Running::wait_or_interrupt` and `NamedEvent::wait_or_interrupt` end a wait early).

  Owns job objects, process creation, named mutexes and events, priority, console handling and taking samples. References `proc-table` and `windows-sys`. Never holds policy: what to kill and when is `gate-watchdog`'s.
- **`gate`** (`crates/gate/`, Windows only): the binary. Owns the subcommands, the wait loop, the run, the journal writes, the `remote.ps1` bridge and `gate box`. References every crate above. Nothing depends on it.

  Its modules so far: `route.rs` (the routing facts read from the routing file, git and the drive table, and the lines of the decision), `slots.rs` (`ThisGate`, the gate's identity built once and shared with the journal; the pool, liveness, take, claim, wake and deletes), `wait.rs` (the wait loop and its lines), `acquire.rs` (`try_slot` and the abandoned-take line) and `journal.rs` (`RunJournal`, the run's journal lines).

  `stop_tree.rs` is `gate stop-tree`: the snapshot, the tree, the gate jobs and the deepest-first terminates.

  Also `run.rs` (the run lifecycle: program, batch refusal, queue, take, launch, wait, verdict, release), `log.rs` (the log, its tail and the failure markers), `environment.rs` (the command's environment and slot marker) and `watch.rs` (the watch of a running command: the sampler, the load-adjusted clock, the stall kill and the Ctrl+C stop).

`boxside/` is `gate box`: `mod.rs` (the verbs and their exits), `payload.rs` (the base64 JSON payload), `preflight.rs` (the bare repo, the work folder and the report lines), `boot.rs` (the boot-time line), `run.rs` (the lock, the git flags, the sync, the command and the back commit), `forward.rs` (the pipes forwarded to stdout and stderr) and `stop.rs` (terminating the job).

## Integration Footguns

- **Change a file format** (a field, a type, a file name, an object name) → also change `gate-state`, re-capture its fixtures (`crates/gate-state/tests/state/fixtures/README.md`), raise `v` when an old reader would misread it, update [design.md, Formats](design.md#formats), and send ops-tower a repo inbox request, since it reads every format through a pinned rev of `gate-state`.
- **Change a CLI spelling** → also change the compatibility layer in `gate-args`, and every reader of command-line text: ops-tower's activity join and the hooks that inspect a gated command (inventory section 3, "Process-visible facts") match both spellings until the layer goes.
- **Change a stable output line** (STALLED, TIMED OUT, BACKSTOP, `waiting for the machine (critical)`, `Full output:`) → it is a breaking change for the scripts in inventory section 3 and the built-in marker regex; prose lines change freely.
- **Write a test that starts `gate.exe`** → give it a non-default state root (`--state-dir`): a gate on the default root takes the machine's real slots and writes the real journal, where it fights every session's gates.
- **Change the cmd.exe word rules** → the gate and `gate box` share them in `gate-args`; a fix in one place is a fix in both, and its test covers both callers.
- **Change the slot marker or a kernel object name** → nested gates, `gate stop-tree` and ops-tower's mutex probe all read names; the root hash rule in [design.md, State root](design.md#state-root) applies to every name.
- **Change `gate-state` or `proc-table`'s public API** → ops-tower builds against them by git rev; a breaking change needs its matching change there, by inbox request.

## Test locations

- `crates/gate-state/tests/state/`: every format against its fixtures, claims, counts, the critical and queue views, journal reading. Fixtures in `crates/gate-state/tests/state/fixtures/`.
- Unit tests inside each pure crate (`gate-watchdog`, `gate-args`, `gate-router`, and `gate-state`'s pure parts): run on Windows and on Linux. Quoting round-trips and path rewrites are property tests.
- `crates/gate/tests/`: the black-box suite, a test target with `required-features = ["test-seams"]`. A new behaviour of the binary gets a case here, with its own state root and ordering-only asserts. `suite/install.rs` runs `tools/install.ps1` against a temporary `LOCALAPPDATA` and registry key.
- Run everything through the gate with `cargo test --workspace --profile test-release --all-features`; the pure crates alone on Linux with `cargo test` on those packages.
