# gate — architecture

gate is a Cargo workspace whose `gate` binary (`gate.exe`) queues heavy commands onto a fixed number of CPU slots, watches them and kills runaway process trees. Its layers, bottom up: the shared state crates (`gate-state`, `proc-table`), the pure rule crates (`gate-watchdog`, `gate-args`, `gate-router`), the Win32 layer (`gate-win32`) and the binary that composes them.

The rule that shapes it: every file and kernel object another process sees is defined once, in `gate-state`, and the pure crates hold no Windows types, so they build and test on Linux. The design is [design.md](design.md); terms used in a project sense are in the [glossary](GLOSSARY.md).

`gate-state` and `proc-table` exist (moved in from ops-tower with their history, GATE-4), and so do `gate-args` and the `gate` binary's skeleton (GATE-32).

`gate-win32` exists with the named mutexes and events (GATE-33), and the `gate` binary has the slot loop (GATE-34, GATE-30), `gate stop-tree` (GATE-57) and the box side's `boot` and `preflight` verbs (GATE-59), its `run` and `stop` verbs (GATE-60) and its `outputs` verb (GATE-44 part B). `gate-watchdog` exists as a pure crate (GATE-56), and the `gate` binary uses it through `watch.rs` (GATE-58).

`gate-router` exists as a pure crate (GATE-66): the routing decision, `remote.json` parsing, the `-like` matcher, the path rewrite and the work-folder key. The `gate` binary asks it for the routing decision through `route.rs`.

## Layers

- **`proc-table`** (`crates/proc-table/`): owns the process snapshot model (`ProcessInfo`, `ProcessTable`, `ProcessTree` with its `descendants`) and its Windows reader, plus `command_line_of(pid)`, another process's command line read from its memory, and `parent_pid_of(pid)`. References `windows-sys` in its `win32` module only. Never depends on any gate crate: ops-tower and its other crates use it too.
- **`gate-state`** (`crates/gate-state/`): owns every file format in the state root, their readers and writers, the path and object-name rules, journal history, the learned durations library (`durations.rs`: key, estimate, store and rebuild) and the dashboard state ops-tower shows. References `proc-table`. Never depends on `gate-win32`, `gate-watchdog`, `gate-router` or the binary, and its API exposes no `windows` or `windows-sys` types.

  It reads two layouts, told apart by `Generation` (`model.rs`; `Generation::detect` looks for `%LOCALAPPDATA%\gate\cutover.flag`, and `StateInputs.generation` carries the answer). `v1.rs` is `gate.exe`'s, under the state root (`counts_path`, `read_counts`).

  `counts.rs`, `claims.rs`, `remote.rs`, `state.rs` and `win32.rs` (`slot_count_path`, `live_inputs`, `dashboard_state`) are what ops-tower uses; the `gate` binary never does. They read the PowerShell gate's layout under `%LOCALAPPDATA%\gate\` until the flag exists and then `gate.exe`'s under `%LOCALAPPDATA%\gate\v1\` (a slot's row also reads the PowerShell root's claims while its mutex is open), with the waiters taken from its tickets.

  `cutover.rs` is what `gate cutover` writes: `write_cutover_flag` (the flag, holding its write time in RFC 3339 UTC, replacing any flag there) and `copy_slot_counts_to_v1` (the PowerShell gate's counts into the default root's `v1\slot-counts.json`, never replacing a file there; its outcome is `CountsCopy`).

  `drain.rs` is the cutover drain's read-only view of the PowerShell gates still alive: `powershell_gates` lists the heavy, light and remote-slot claims, the critical claim and every ticket, by the dashboard's liveness rule and sorted by `since`, and counts a file it cannot read in `unreadable`.

  `win32.rs`'s `Win32MutexProbe` counts a mutex closed only when no process holds the name.

  `counts.rs` also writes the counts files for ops-tower's Gates tab (`apply_slot_count`, `write_slot_counts`): the PowerShell layout's file, then `gate.exe`'s `v1\slot-counts.json` beside it. `apply_slot_count` keeps the other pool's valid count, replaces a missing, blank, invalid or non-object file, and fails with `ApplyError::Read` on a file that exists but cannot be read, leaving it untouched.
- **`gate-watchdog`** (`crates/gate-watchdog/`, pure): owns the free-share, load-adjusted clock, stall, ceiling and backstop arithmetic over samples (`share.rs`, `watch.rs`, including `measure_cpu` and the progress that build servers and the WSL VM add).

  It also owns the classifiers of build servers, build clients and `wsl` commands over names and command lines (`servers.rs`: `is_build_server`, `is_compiler_server` and `is_compiler_image`, which takes the test seam's image name; with the build servers' priority rule `server_target` and `server_left` over an `Option<PriorityClass>`, `None` being an unreadable class), and the kill lines.

  It also owns the pure formatting of the diagnostics block a kill writes (`diagnostics.rs`: `lines`, `failed_block`, `failed_line` and the caps `JOB_LINES` and `OUTSIDE_LINES`).

  The box heartbeat's beat rule and pump are in `heartbeat.rs`.

  The cores hint's average, peak and free cores and its verdict over a slot kind are in `cores.rs`, fed by the samples in `watch.rs`. References nothing of the gate's but plain data types. Never reads a clock, a process or a file itself: the clock, the samples and the CPU are injected.
- **`gate-args`** (`crates/gate-args/`, pure): owns the gate's own argv (the subcommand CLI and the compatibility layer), C-runtime and cmd.exe quoting, the `%VAR%` refusals and the PATHEXT resolution rules; the command's words are in `cmdline.rs` (C-runtime quoting, `command_text`), `batch.rs` (batch targets, cmd.exe quoting, refusals) and `program.rs` (program resolution). Never depends on `gate-win32`; the environment and file lookups it needs are injected.
- **`gate-router`** (`crates/gate-router/`, pure): owns the routing decision (`decide`, `Route`), `remote.json` parsing (`config.rs`), the `-like` matcher (`like.rs`), the in-worktree path rewrite (`rewrite.rs`), the work-folder key (`key.rs`), over strings; `decide.rs` also drops `--no-build` of a dotnet `test` or `run` (the same drop the local run asks for), reads a `pwsh` script's wrapped dotnet command, and pins `SourceRevisionId` on the builder's words.

  Reads no file, runs no git, ssh or process, and has no clock or environment: each fact comes through its `Facts` trait, asked only at the rule that needs it. Never depends on `gate-win32`, `windows-sys` or any other gate crate; its only dependencies are `serde_json` and `sha2`.
- **`gate-win32`** (`crates/gate-win32/`, Windows only).

  Built so far: named mutexes, events and process start times (the gate's own, and `process_start_of(pid)` for another process, `None` for a pid that is gone or exited).

  Also `move_no_replace` (`file.rs`: a rename that never replaces its target, which a sync-back moves fetched objects with), `device_target` (`device.rs`: the target of a drive letter's DOS device over `QueryDosDevice`, which the routing facts use to follow `subst` drives), `system_directory` (the folder holding cmd.exe), `runs_below_normal` (the gate's own priority class), `win32_message`, `boot_time` (when the machine booted).

  Also job objects (`Job`: create, `create_kill_on_close` (a job whose last handle ends its processes, never handed to a piped command), terminate, process ids, `accounting`; `OpenedJob`: open by name with query and terminate access, `open_to_list` with query access only (the priority guard uses it), process ids, terminate).

  Process stopping is `StoppableProcess` (open, created, parent_pid, in_job, exited, wait, exit_code, terminate; in `tree.rs`; `Job::holds` is the job-membership question it asks), and `WaitableProcess` (open, created, wait; also in `tree.rs`) is a process opened only to wait for its end, which `gate burn` uses for its parent.

  `OpenedJob::holds(pid, created)` answers the membership question for another gate's job as a `Membership`: `Member`, `Outside`, `NotOpened` for a process it cannot open (no process has the pid, or access is denied), or `Reused` when the creation time differs, a failed membership query being `Err`; it and `Job::holds` go through `job::holds`. `working_set(pid)` (`memory.rs`) is another process's working set in bytes, `None` for a pid that is gone or exited.

  Suspended process creation is `Launch` → `Suspended` → `Running`, whose `Launch.output` is a `LaunchOutput`: `Files { log, err_log }` for the command's output files, or `Piped`, which has stdin and stdout piped and the gate's own stderr (`Suspended::take_pipes` hands back its `StdioPipes { stdin, stdout }`). Also `EnvironmentBlock`, `same_variable_name` and `PriorityClass`.

  The box's piped launch is `PipedLaunch` → `PipedSuspended` (in `piped.rs`: a `PipedConsole` that is hidden or attached to the caller's, breakaway from the caller's job, two pipes and a query-only job handle inherited), with `check_plain_file` and `breakaway_refused`.

  `PipedLaunch::start_suspended_within_fed` (in `piped.rs`) is the same suspended start in a job with stdin piped as well, a `PipedFed` holding the write end, which `gate push` feeds the exe through.

  `console.rs` is the box's UTF-8 console: a `Donor` (a `cmd.exe` put in the command's job) and `Utf8Console`, which attaches the process to the donor's console, sets the code pages, and returns through a keeper. `event.rs`'s `NamedEvent` also gives the named manual-reset event of a job's stop signal (`create_new_manual` by the run, `open_to_set` by `stop`).

  Both launches create the process through the shared `create.rs` (`check_launch`, `startup_info`, `AttributeList`, `create_process`, `create_inheriting`), so the refusals before the call and the startup information are one code path.

  The spawn lock (in `create.rs`) is held while the layer starts any process: `create_inheriting` makes inheritable copies of a launch's handles under it, so the gate's own handles are never inheritable, and `spawn(&mut Command)` starts a std `Command` under the same lock. A std spawn anywhere in the gate goes through `gate_win32::spawn`.

  `priority.rs` is another process's priority class: `Priority`, `priority_of(pid)` and `set_priority(pid, priority)`, `None` for a pid that is gone and an error for a class that cannot be read (`priority_of` asks for `PROCESS_QUERY_INFORMATION`); the gate takes that error as an unknown class.

  Also the samples in `times.rs` (`system_times`, `process_times`, `file_time_now`) and the Ctrl+C handler in `interrupt.rs` (`Interrupt`: install, is_raised, raise; `Running::wait_or_interrupt` and `NamedEvent::wait_or_interrupt` end a wait early).

  Owns job objects, process creation, named mutexes and events, priority, console handling and taking samples. References `proc-table` and `windows-sys`. Never holds policy: what to kill and when is `gate-watchdog`'s.
- **`gate`** (`crates/gate/`, Windows only): the binary.

  Owns the subcommands, the wait loop, the run, the journal writes, the remote pool and client call of a routed run, and `gate box`. The client of a routed run is the Rust client over ssh, chosen in `remote/mod.rs`.

  The Rust client in `remote/{client,install,outputs,parity,payload,retry,syncback,transport,watchdog}.rs`, with the snapshot beside it, is in every build; the local transport, the scripted client and the seams that pick a client are in test-seams builds only. `gate push` uses the transport's ssh words and `Ssh::find`. The git runner `remote/git.rs` is in every build, for `route.rs`, the client and the box preflight's SDK read.

  References every crate above. Nothing depends on it.

  Its modules so far: `route.rs` (the routing facts read from the routing file, git and the drive table, and the lines of the decision), `remote/`, in which `mod.rs` holds the `RemoteClient` a routed run calls, its call and outcome, and the scripted client of the `test-seams` build, and a client that cannot start makes a routed run fall back with reason `client`.

  `client.rs` holds `RustClient`, whose `ready()` (`&mut self`, returning `Result<(), String>`) looks for ssh on the routed attempt's first need, before any key lock, ticket or slot; no usable ssh makes the run fall back `client`. Its ssh calls start in the system folder with `NoDefaultCurrentDirectoryInExePath=1` (`call_command`).

  `git.rs` is the git runner shared with `route.rs`, which reads git's output through pipes and caps it at 16 MiB for the calls the client reads, and whose bounded start and wait also runs `dotnet --list-sdks` (`sdk_listing`): this PC's for the parity check, and the builder's for `gate box preflight`.

  `launch.rs` starts a call in an anonymous kill-on-close job (suspended, assigned, resumed) and holds the kill and drain waits, shared by `git.rs` and `client.rs`.

  `snapshot.rs` is the snapshot and the bridge commit of the Rust remote client, reached only by `--test-remote-snapshot`.

  `outputs.rs` is the client's end of a routed run's outputs: the outputs manifest it sends, the pending marker and the box's `gate-remote-outputs: ` line.

  `parity.rs` is the client's pure toolchain parity rules: the SDK pin read from `global.json`, the nine rollForward policies and the no-pin major rule.

  `install.rs` is the client's install of the fetched outputs archive: it unpacks into a stage, checks, skips each member that counts as tracked (listed in one `git ls-files -z -s` through `Attempt::git_bytes`, under a submodule, or below a nested `.git`; unless a `--bring-tracked` glob matches it) or whose PC file is in use, rewrites the box's work folder in two files and moves each file into the worktree.

  `syncback.rs` is the client's sync-back, which fetches the builder's back ref and applies it to the worktree.

  `watchdog.rs` is the client's pure rules for when a call is killed, its kill line, the watchdog's tick, the stall window and the 64 KiB line cap.

  `client.rs` runs the calls in anonymous kill-on-close jobs and holds the watch, the stop and Ctrl+C.

  Beside them are `slots.rs` (`ThisGate`, the gate's identity built once and shared with the journal; the pool, liveness, take, claim, wake and deletes), `wait.rs` (the wait loop and its lines, the barrier of a critical request ahead, the reserved light slots beside it, the lend of a light parent's slot and the writing of the pause marker, over `Waiter`, the wake event, ticket, sleep and heartbeat that `Wait` and the critical `MachineWait` share).

  Beside them are also `acquire.rs` (`try_slot` and the abandoned-take line), `journal.rs` (`RunJournal`, the run's journal lines, and `write_then`, which runs a step in the hold of a line's journal mutex) and `durations.rs` (`RunDurations`: the run's durations key, the expected-time line, the filing of its release in the durations store and the store's rebuild, over the `gate-state` library).

  `machine.rs` is a critical gate's wait for the machine: the critical mutex, the drain, the take of every heavy and unreserved light slot, its lines, the snapshot its `take` journals and the release.

  `pause.rs` is the pause marker: the writer a waiting gate under a parent's slot refreshes on each pass of its wait, and the reader (`PauseReader`, over `live_child_pause_with`) the watchdog in `watch.rs` calls on each sample.

  `stop_tree.rs` is `gate stop-tree`: the snapshot, the tree, the gate jobs and the deepest-first terminates.

  `stopping.rs` is the checked open of one process a snapshot listed, shared by `stop_tree.rs` and `escaped.rs`: the process is checked through its own handle to be the one the snapshot saw before it is terminated.

  `escaped.rs` is the look for the processes that left a command's job (a packaged desktop app a non-packaged descendant started, and what it started) and the kill that ends them: `Reach` (the job, the test seam's server image and the state root), `look`, `terminate`, and the kill's lines; and `Recorded`, what the watch's samples found outside the job (pid, start, parent), which every kill of a running command ends too. `run.rs` calls it on every kill of a `gate run` command.

  `cutover.rs` is `gate cutover`: the counts copy, the flag write and the drain over `gate-state`'s `powershell_gates`, with its lines, the confirmation window and the Ctrl+C stop.

  `burn.rs` is `gate burn`: the checks of `--cores` against the machine's logical processors, the burner threads, and the wait on the process that started it.

  `expect.rs` is `gate expect`: a lock-free reader of `durations.json` that keys the command here and for each builder and prints the expected-time line of each place with an estimate, or `no history`; it queues for nothing and writes nothing.

  `push.rs` is `gate push`: it reads the builders from the routing file (`read_remote_json`, `Config::builders`) and the installed exe, then makes one ssh call per builder through `transport.rs`'s `ssh_words` and `Ssh::find`, feeding the exe as base64 on stdin to an embedded PowerShell script, and maps the script's `gate-push: ` lines to the `push: ` lines.

  Also `run.rs` (the run lifecycle: program, batch refusal, queue, take, launch, wait, verdict, release), `log.rs` (the log, its tail and the failure markers), `environment.rs` (the command's environment and slot marker) and `nesting.rs` (the slot marker a gate was started under: its parse, the parent's liveness, and the covered, refused or own-slot decision, and the search for a stand-in when the parent has ended).

  `late.rs` is the late take of a covered heavy or light gate: the watch of its parent gate through a waitable handle, the stand-in search once the parent ends, and the queue and take of a slot of its own kind beside the running command, driven one step a wake by the watch loop in `watch.rs`; `covered.rs` rewrites the covered marker's `kind` to `none` when the watch is given up.

  `no_build.rs` is the facts of a local dotnet `--no-build` run: the nothing-back record read as itself, the obj check (the projects without `obj\project.assets.json`, the solution readers, the `Directory.Build.*` skip) and the git calls for the worktree and its tracked projects; `run.rs` decides the drop and the clear from it.

  `nesting/binding.rs` judges whether the marker binds to the parent gate's job: the walk from this gate up a process snapshot, pure over an injected job, snapshot and `holds`.

  And `watch.rs` (the watch of a running command: the sampler, the pause read, the load-adjusted clock, the stall kill and the Ctrl+C stop), `servers.rs` (the build servers outside the job and the build client inside it, read once per sample) and `priority.rs` (the per-watch `Prioritizer` that lowers or raises the classified build servers, and `OtherGates`, the guard it reads, at most once a pass and only when a server to move asks, from the tickets, claims and other gates' jobs).

`boxside/` is `gate box`: `mod.rs` (the verbs and their exits), `payload.rs` (the base64 JSON payload), `preflight.rs` (the bare repo, the work folder and the report lines), `boot.rs` (the boot-time line).

It also holds `run.rs` (the lock, the git flags, the sync, the command, the back commit and the call to pack outputs), `outputs.rs` (the PC's manifest read, the old-archive prune, the pack of a run's outputs, the 50 GiB trim of the outputs folder and the `outputs` verb that sends and deletes the archive).

It also holds `tools.rs` (the dotnet tool restore and its `<Work>.tools` record), `forward.rs` (the pipes forwarded to stdout and stderr), `heartbeat.rs` (the command heartbeat: the job's and the build servers' CPU on `gate-watchdog`'s `Pump`), `inflight.rs` (the `inflight` verb: which locks under `{Root}\work` a routed run holds) and `stop.rs` (terminating the job).

`outputs/` is a routed run's outputs, shared by both ends: `glob.rs` (the output globs and the exclusions, case-insensitive), `walk.rs` (the matching files below a folder, skipping links and junctions; `walk_with_refused` also notes the files refused for their names, reading a folder whose name is not plain through a verbatim path to count them), `hash.rs` (SHA-256 and `is_lower_hex`).

Also in it are `manifest.rs` (the PC's manifest and `select`, which picks the files a run changed or the PC lacks), `cache.rs` (the PC's hash cache: the hashes of its last built manifest, reused for a file whose size and last write still match) and `archive.rs` (`pack` and `unpack` of the `.tar.zst`, with strict refusals and limits).

`outputs/names.rs` holds `is_git_s` and `is_lfs_config`, the `.git*` and `.lfsconfig` names that the globs and the sync-back both refuse, and `is_plain_path`, `is_plain_part` and `is_device`, the plain-path rule the globs, the walk, the pack and the unpack share.

The box packs and sends with it (`boxside/outputs.rs`, GATE-44 part B); the PC's install is `remote/install.rs` (part D). The Rust client builds the manifest, keeps the pending marker, reads the box's outputs line and fetches the archive (`remote/outputs.rs`, parts C1 and C2), then verifies and installs it (`remote/install.rs`). `boxside/payload.rs` holds its payload accessors.

## Integration Footguns

- **Change a file format** (a field, a type, a file name, an object name) → also change `gate-state`, re-capture its fixtures (`crates/gate-state/tests/state/fixtures/README.md`), raise `v` when an old reader would misread it, update [design.md, Formats](design.md#formats), and send ops-tower a repo inbox request, since it reads every format through a pinned rev of `gate-state`.
- **Change a CLI spelling** → also change the compatibility layer in `gate-args`, and every reader of command-line text: ops-tower's activity join and the hooks that inspect a gated command (inventory section 3, "Process-visible facts") match both spellings until the layer goes.
- **Change a stable output line** (STALLED, TIMED OUT, BACKSTOP, `waiting for the machine (critical)`, `Full output:`) → it is a breaking change for the scripts in inventory section 3 and the built-in marker regex; prose lines change freely.
- **Write a test that starts `gate.exe`** → give it a non-default state root (`--state-dir`): a gate on the default root takes the machine's real slots and writes the real journal, where it fights every session's gates.
- **Change the cmd.exe word rules** → the gate and `gate box` share them in `gate-args`; a fix in one place is a fix in both, and its test covers both callers.
- **Change the slot marker or a kernel object name** → nested gates (`crates/gate/src/nesting.rs::parse` reads the marker, and `nesting/binding.rs` opens the parent's job by the same name to check the marker binds to it), `gate stop-tree` and ops-tower's mutex probe all read names; the root hash rule in [design.md, State root](design.md#state-root) applies to every name.
- **Change how a kill reaches a command's tree** → the escaped-tree kill in `crates/gate/src/escaped.rs` (a `gate run` kill) and the other kill sites (the box's stop, the remote client, `gate push`: GATE-140) must agree on what is ended and what is spared, build servers included.

  The stall check, the cores and the clock already count the escaped tree under the job's members (`escaped::outside_the_job` in each sample), and every kill of a running `gate run` command ends the recorded escaped processes too, whose launcher may have exited.
- **Change `gate-state` or `proc-table`'s public API** → ops-tower builds against them by git rev; a breaking change needs its matching change there, by inbox request.

## Test locations

- `crates/gate-state/tests/state/`: every format against its fixtures, claims, counts, the critical and queue views, journal reading. Fixtures in `crates/gate-state/tests/state/fixtures/`.
- Unit tests inside each pure crate (`gate-watchdog`, `gate-args`, `gate-router`, and `gate-state`'s pure parts): run on Windows and on Linux. Quoting round-trips and path rewrites are property tests.
- `crates/gate/tests/`: the black-box suite, a test target with `required-features = ["test-seams"]`. A new behaviour of the binary gets a case here, with its own state root and ordering-only asserts. `suite/install.rs` runs `tools/install.ps1` against a temporary `LOCALAPPDATA` and registry key.
- Run everything through the gate with `cargo nextest run --workspace --all-features --cargo-profile test-release`; the pure crates alone on Linux with `cargo nextest run` (or `cargo test`) on those packages. Which tests a change reaches, as nextest filtersets: [test-map.md](test-map.md).
