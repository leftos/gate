# gate — architecture

gate is a Cargo workspace whose `gate` binary (`gate.exe`) queues heavy commands onto a fixed number of CPU slots, watches them and kills runaway process trees. Its layers, bottom up: the shared state crates (`gate-state`, `proc-table`), the pure rule crates (`gate-watchdog`, `gate-args`, `gate-router`, `gate-wire`, `gate-inputs`), the Win32 layer (`gate-win32`), the binary that composes them and, beside it, the Unix box (`gate-box-unix`).

The rule that shapes it: every file and kernel object another process sees is defined once, in `gate-state`, and the pure crates hold no Windows types, so they build and test on Linux. The design is [design.md](design.md); terms used in a project sense are in the [glossary](GLOSSARY.md).

`gate-state` and `proc-table` exist (moved in from ops-tower with their history, GATE-4), and so do `gate-args` and the `gate` binary's skeleton (GATE-32).

`gate-win32` exists with the named mutexes and events (GATE-33), and the `gate` binary has the slot loop (GATE-34, GATE-30), `gate stop-tree` (GATE-57) and the box side's `boot` and `preflight` verbs (GATE-59), its `run` and `stop` verbs (GATE-60) its `outputs` verb (GATE-44 part B) and its `inflight` verb (GATE-175) and its `inputs` verb (GATE-22), its `lfs` verb (GATE-469), its `register-desktop` verb and its `prune` verb (GATE-571).

`gate-watchdog` exists as a pure crate (GATE-56), and the `gate` binary uses it through `watch.rs` (GATE-58).

`gate-router` exists as a pure crate (GATE-66): the routing decision, `remote.json` parsing, the `-like` matcher, the path rewrite and the work-folder key. The `gate` binary asks it for the routing decision through `route.rs`.

`gate-wire` is the box request payload both the PC client and every box parse (GATE-605): the base64 JSON reader, its key accessors and refusal lines, and the path rules of the box that reads it, `PathForm::Windows` (drive paths, full-path compares without case, `Local\` job names) or `PathForm::Unix` (one spelling per absolute path, byte compares, `/` joins). It also holds the gate's version text, `build_version` (the package version from `[workspace.package]` plus `GATE_BUILD_ID`), and the version parse the tool probes share (`version_of`, `first_version`). It holds `build_server_settings`, the build-server variable names every box strips from a command's environment before it sets the payload's. Its `stamp` module is the format of a run's log line, `<local µs time with UTC offset> <out|err|gat> <text>`: `stamped`, `unstamped` (the strict parse, a plain line whole), `Tag`, and the wording of the process lines (`root_text`, `spawn_text`, `exit_text`, `missed_text`, `left_text`, `stopped_text`, `is_process_line`), which no other crate words. It builds on any OS and depends only on `gate-args`, `gate-router` and `jiff`.

`gate-inputs` is what the Windows box and the Unix box must judge alike about the files of a routed run's inputs and outputs: `names` (the `.git*` and `.lfsconfig` names and the plain-path rule), `hash` (`Hashing`, `sha256_of`) and `manifest` (`Manifest`, `Held`, `HeldBy`, `Stamp`, `MANIFEST_LIMIT`, `read_sent` and `refused_path`, the check of the paths a sent manifest names, and `Listing`, `Chosen`, `select` and `hash_possible_copies`).

Its `archive` is the member reader and the `Place` trait; `pack` (`Packer`, `Packed`, `window_log`), `glob` (`Globs`, `regex_upto`) and `walk` (`Found`, `Walked`, `relative_path`). It depends on `regex`.

Its `archive` module holds the `.tar.zst` member reader `read_members`, its checks and limits, `sent_limit`, `UnpackError`, and the `Place` trait each box writes through, with `extract` and `FolderBudget`.

It makes no OS calls, builds and tests on any OS, and must never depend on `gate` or any Windows code.

`gate-box-unix` is the gate box of a macOS builder (GATE-607), the bin `gate-box`: `box preflight`, `boot`, `run`, `stop`, `inputs`, `outputs` and `prune`, speaking the wire of the Windows box. It builds on any OS, but its verbs are `cfg(unix)`. The run checks a payload's `InputsDigest` (`run.rs`, `inputs_matched`, over `inputs::unmatched`) and brings outputs back through `outputs.rs`; `SentDigest` and `LfsDigest` are not built, so a run carrying either is still refused.

## Layers

- **`proc-table`** (`crates/proc-table/`): owns the process snapshot model (`ProcessInfo`, `ProcessTable`, `ProcessTree` with its `descendants`) and its Windows reader, plus `command_line_of(pid)`, another process's command line read from its memory, and `parent_pid_of(pid)`; `Win32ProcessTable::try_snapshot_without_command_lines` is a snapshot that reports its failure and skips the command-line reads, which the box's sweep of a failed desktop hand-off uses.

  References `windows-sys` in its `win32` module only. Never depends on any gate crate: ops-tower and its other crates use it too.
- **`gate-state`** (`crates/gate-state/`): owns every file format in the state root, their readers and writers, the path and object-name rules, journal history, the learned durations library (`durations.rs`: key, estimate, store and rebuild) and the dashboard state ops-tower shows. References `proc-table` and `gate-router` (`remote.rs` reads `remote.json` through `gate_router::Config`, and `state.rs` names pools by `gate_router::builder_id`, for the dashboard's `builders`), which brings `toml` into its build. Never depends on `gate-win32`, `gate-watchdog` or the binary, and its API exposes no `windows` or `windows-sys` types.

  It reads two layouts, told apart by `Generation` (`model.rs`; `Generation::detect` looks for `%LOCALAPPDATA%\gate\cutover.flag`, and `StateInputs.generation` carries the answer). `v1.rs` is `gate.exe`'s, under the state root (`counts_path`, `read_counts`).

  `counts.rs`, `claims.rs`, `remote.rs`, `state.rs` and `win32.rs` (`slot_count_path`, `live_inputs`, `dashboard_state`) are what ops-tower uses; the `gate` binary never does. They read the PowerShell gate's layout under `%LOCALAPPDATA%\gate\` until the flag exists and then `gate.exe`'s under `%LOCALAPPDATA%\gate\v1\` (a slot's row also reads the PowerShell root's claims while its mutex is open), with the waiters taken from its tickets.

  `cutover.rs` is what `gate cutover` writes: `write_cutover_flag` (the flag, holding its write time in RFC 3339 UTC, replacing any flag there) and `copy_slot_counts_to_v1` (the PowerShell gate's counts into the default root's `v1\slot-counts.json`, never replacing a file there; its outcome is `CountsCopy`).

  `drain.rs` is the cutover drain's read-only view of the PowerShell gates still alive: `powershell_gates` lists the heavy, light and remote-slot claims, the critical claim and every ticket, by the dashboard's liveness rule and sorted by `since`, and counts a file it cannot read in `unreadable`.

  `win32.rs`'s `Win32MutexProbe` counts a mutex closed only when no process holds the name.

  `counts.rs` also writes the counts files for ops-tower's Gates tab (`apply_slot_count`, `write_slot_counts`): the PowerShell layout's file, then `gate.exe`'s `v1\slot-counts.json` beside it. `apply_slot_count` keeps the other pool's valid count, replaces a missing, blank, invalid or non-object file, and fails with `ApplyError::Read` on a file that exists but cannot be read, leaving it untouched.
- **`gate-watchdog`** (`crates/gate-watchdog/`, pure): owns the free-share, load-adjusted clock, stall, ceiling and backstop arithmetic over samples (`share.rs`, `watch.rs`, including `measure_cpu` and the progress the WSL VM adds).

  It also owns the `wsl` command test over a command's first word (`watch.rs`: `is_wsl_command`) and the kill lines.

  It also owns the pure formatting of the diagnostics block a kill writes (`diagnostics.rs`: `lines`, `failed_block`, `failed_line` and the caps `JOB_LINES` and `OUTSIDE_LINES`).

  The box heartbeat's beat rule and pump are in `heartbeat.rs`.

  The cores hint's average, peak and free cores and its verdict over a slot kind are in `cores.rs`, fed by the samples in `watch.rs`. References nothing of the gate's but plain data types. Never reads a clock, a process or a file itself: the clock, the samples and the CPU are injected.
- **`gate-args`** (`crates/gate-args/`, pure): owns the gate's own argv (the subcommand CLI and the compatibility layer), C-runtime and cmd.exe quoting, the `%VAR%` refusals and the PATHEXT resolution rules; the command's words are in `cmdline.rs` (C-runtime quoting, `command_text`), `batch.rs` (batch targets, cmd.exe quoting, refusals) and `program.rs` (program resolution). Never depends on `gate-win32`; the environment and file lookups it needs are injected.
- **`gate-router`** (`crates/gate-router/`, pure): owns the routing decision (`decide`, `Route`), `remote.json` parsing (`config.rs`), the `-like` matcher (`like.rs`), the in-worktree path rewrite (`rewrite.rs`, which also rewrites a path into a declared sibling, from a `RewritePlace`, judges which words name a path outside the worktree, and derives the program name a first word naming a program by such a path is sent as), the work-folder key and the folder-name rule `is_layout_name` and its character rule `is_layout_char` (`key.rs`), over strings.

  `escape.rs` holds `escaped` and `is_reordering_mark`, the one-line escaping of outside text.

  `decide.rs` also exports `target(config, place, facts)`, where a worktree's routed work runs and how its work folder is laid out (host, siblings, key, inputs), and `builder_words(target, words, facts)`, a command's words for that builder (`--no-build` dropped, paths rewritten, `./name` marked, `SourceRevisionId` and `PathMap` stamped); `decide` uses both.

  `warm.rs` holds the builder warm-up's pure parts: the `.gate/warmup.toml` reader, its hash, the judge and the lines it says (a routed run says them from `crates/gate/src/route.rs` and `run.rs`, and `gate check` words the same cases from the helpers `warming_text`, `record_problem_text`, `lock_problem_text` and `shown_value`). It also exports `parse_failure` and `spelled`, the TOML parse-failure text and key spelling that the gate's `remote/siblings.rs` and `remote/toolchain.rs` readers share.

  `desktop.rs` holds the reader of a repo's `.gate/desktop.toml` (`read_desktop`: the byte order mark skipped, at most `MOST_PATTERNS` of 32 `-like` patterns, the first problem wins); `decide.rs`'s `check_desktop` applies it, with `config.rs`'s `allowed_desktop` consent, to a matched command after the siblings checks.

  `local.rs` holds the reader of a repo's `.gate/local.toml` (`read_local`, the same shape with `patterns`), which `decide.rs`'s `check_local` applies right after the repo's patterns match, before the siblings and desktop checks; `env.rs` holds the reader of its `.gate/env.toml` (`read_env`: at most `MOST_PREFIXES` of 32 ASCII name prefixes, none starting `GATE_`) and `problem_line`; `list.rs`'s `read_list` is the one-key list reader the three share.

  `watch.rs` holds `dropped_env`, the names of a caller's environment a routed run does not send (`NuGetAudit`, `RUSTFLAGS`, `RUSTDOCFLAGS` and the prefixes `NUGET_`, `MSBUILD`, `CARGO_BUILD_`, `CARGO_PROFILE_`, and any prefix the repo's `.gate/env.toml` declares), and `dropped_env_line`, the line the run says for them, which `crates/gate/src/route.rs` (`dropped_line`) says after a routed run's other route lines.

  `decide.rs` also exports `sibling_root(root, name)`, where a sibling lies beside a worktree root, which the routing decision and `gate check` both use.

  `decide.rs` also drops `--no-build` of a dotnet `test` or `run` (the same drop the local run asks for), reads a `pwsh` script's wrapped dotnet command, and pins `SourceRevisionId` and maps the builder's trees to the PC's roots as `PathMap` on the builder's words.

  The `PathMap` word is built by `stamp` and `path_map_word`, and `sets_property` reads the opt-out; the trees come from `Facts::box_trees`, which `route.rs` answers through `remote::box_trees`, pairing them with `outputs::trees_of`, the pairing the install uses, and refusing a root the word cannot carry).

  `RemoteRun.source_revision` carries the worktree's HEAD sha, which `run.rs` (`routed_env`) sends as the `SourceRevisionId` environment variable.

  Reads no file, runs no git, ssh or process, and has no clock or environment: each fact comes through its `Facts` trait, asked only at the rule that needs it. Never depends on `gate-win32`, `windows-sys` or any other gate crate; its only dependencies are `serde_json` and `sha2`.
- **`gate-win32`** (`crates/gate-win32/`, Windows only).

  Built so far: named mutexes, events and process start times (the gate's own, and `process_start_of(pid)` for another process, `None` for a pid that is gone or exited).

  Also `move_no_replace` (`file.rs`: a rename that never replaces its target, which a sync-back moves fetched objects with), `device_target` (`device.rs`: the target of a drive letter's DOS device over `QueryDosDevice`, which the routing facts use to follow `subst` drives), `system_directory` (the folder holding cmd.exe), `runs_below_normal` (the gate's own priority class), `win32_message`, `boot_time` (when the machine booted), `cancel_synchronous_io` (`thread.rs`: cancels the read a thread is waiting on, which the box's output drain uses to tell a pipe a leftover holds open from a reader that is only behind), `Gpu3dWindow` (`gpu.rs`: the GPU's 3D use per adapter over a window, read from the PDH counters, which an `--alone` run's load snapshot logs).

  Also `registry_subkeys` (`registry.rs`: the subkeys of one key of a `Hive`, each with one string value, read-only, which the netfx-sdk probe lists the .NET Framework SDKs with).

  Also job objects (`Job`: create, `create_kill_on_close` (a job whose last handle ends its processes, never handed to a piped command), terminate, process ids, `accounting`, `remember(Option<Sender<JobEvent>>)` and `finish_events`, which tell a consumer each member's join and end as a `JobEvent` (a spawn always before its exit) and end the still-running ones with `Left` lines; `OpenedJob`: open by name with query and terminate access, `open_to_list` with query access only (`nesting/binding.rs` and `run.rs` use it), process ids, terminate).

  Process stopping is `StoppableProcess` (open, created, parent_pid, in_job, exited, wait, exit_code, terminate; in `tree.rs`; `Job::holds` is the job-membership question it asks), and `WaitableProcess` (open, created, wait; also in `tree.rs`) is a process opened only to wait for its end, which `gate burn` uses for its parent.

  `OpenedJob::holds(pid, created)` answers the membership question for another gate's job as a `Membership`: `Member`, `Outside`, `NotOpened` for a process it cannot open (no process has the pid, or access is denied), or `Reused` when the creation time differs, a failed membership query being `Err`; it and `Job::holds` go through `job::holds`. `working_set(pid)` (`memory.rs`) is another process's working set in bytes, `None` for a pid that is gone or exited.

  Suspended process creation is `Launch` → `Suspended` → `Running`, whose `Launch.output` is a `LaunchOutput`: `Files { log, err_log }` for the command's output files, or `Piped`, which has stdin and stdout piped and the gate's own stderr (`Suspended::take_pipes` hands back its `StdioPipes { stdin, stdout }`). Also `EnvironmentBlock`, `same_variable_name` and `PriorityClass`.

  The box's piped launch is `PipedLaunch` → `PipedSuspended` (in `piped.rs`: a `PipedConsole` that is hidden or attached to the caller's, breakaway from the caller's job, two pipes and a query-only job handle inherited), with `check_plain_file` and `breakaway_refused`.


  `PipedLaunch::start_suspended_within_fed` (in `piped.rs`) is the same suspended start in a job with stdin piped as well, a `PipedFed` holding the write end, which `gate push` feeds the exe through.

  `trust.rs` owns `TRUSTED_OWNERS` (SYSTEM, Administrators and TrustedInstaller, as SID strings; `boxside/msys.rs` takes its owner list from it) and `check_installed_file(path) -> Result<(), Untrusted>`, which judges an installed file, its folder and every folder above it to the volume root, each opened by handle, refusing links, junctions, network locations and a path that resolves elsewhere.

  `trust.rs` also owns `check_work_root(root, walk_stop) -> Result<File, Untrusted>`, which judges the builder's work root (its DACL and owner, the folders above it to the volume root, reparse points, a `subst` or network path), makes a missing one locked, and returns it held (no delete sharing); `Untrusted::is_busy` tells a root another process holds open from an unsafe one. `walk_stop` ends the walk above the root early and is a test seam's alone.

  `gate box` calls it for its own image, for the desktop helper (`boxside/mod.rs`, `helper_trusted`, shared by the preflight and the desktop hand-off) and in the `register-desktop` verb.

  What a run on the builder's interactive desktop needs (`gate-desktop`'s helper calls all of it; `gate box` calls `session.rs`, `mutex.rs`'s `PrivateMutex` and `token.rs`'s `current_account` in its desktop stage, `boxside/run/desktop_run.rs`, and the pipe, adoption, task, launch and job pieces below in its hand-off, `boxside/run/desktop_run/hand_off.rs`):
  - `lib.rs`: `set_default_dll_directories_system32`, the DLL search limited to System32, which the helper's start and every `gate box` verb call first.
  - `pipe.rs`: `PipeServer` and `PipeClient`, a one-instance named pipe under a random name for one user's local client, the client refusing a pipe whose owner, DACL or label is not the server's; `read` and `write_all` on either end are overlapped and bounded by a deadline and wake handles (`PipeRead`, `PipeWrite`); a client refuses a name outside `\\.\pipe\`. Its `wait_any`, `look_at_wake` and the shared decoder of a wait's result (`woken`) also serve `task.rs`.
  - `adopt.rs`: `RemoteProcess` (push and pull handles into and out of another process; `exit_code`, `terminate` and `wait_or_woken`, which gives an `EndWait`, are how the box watches and ends the helper), `QueryOnlyProcess` (another process opened for reads alone, such as its session) and the reads that say what a handed-over process or thread is (parent, creation time, session, image, `user_of`, `thread_is_suspended`); `end_process`, `same_object`, `is_handle_value`, `check_received_output` (a received handle must be a pipe other than the control pipe) and `granted_access` (the access a handle was granted, which `Suspended::adopt` checks).

    A child is never found again by its pid: whoever created it ends it through the process handle it holds.
  - `session.rs`: the console session's id, connect state, user, domain and lock state, and `input_desktop_name`; `token.rs`: `current_user_sid`.
  - `piped.rs`: `DesktopLaunch`, a suspended child on `WinSta0\Default` at normal priority with an explicit handle list; `output_pipes` (`OutputPipes`), the two non-inheritable output pipes whose write ends the box pushes to the helper.
  - `task.rs`: `run_task(&TaskStart, deadline, wake)` starts the registered task `\gate\desktop-helper` in a given session through the Task Scheduler's COM API, once its definition passes the check (enabled, on demand, parallel, priority 4, no battery limits, no time limit, no triggers, one action running the helper with `$(Arg0)` alone, the interactive least-privilege token of the user running gate, an owner of SYSTEM or Administrators, and no one else besides them allowed more than read), and gives `StartedTask::Process(pid)`, or `NoPid` when it was started but no process was seen within `pid_wait`.

    A `TaskArgument` holds only `0-9`, `a-f` and `:`. The COM calls run on a thread of their own in the multithreaded apartment, waited on until the deadline or a wake handle; `taskschd.dll` is loaded once by its full System32 path and never freed, and the class is made from it, never looked up in the registry.

    `NotRegistered`, `SetUpWrong` and `Failed` mean nothing was started; `StartedUnknown`, `TimedOut`, `Woken` and `Unanswered` mean it may have been, and the caller drops its pipe server. Every error text is escaped and cut. `run_task` never registers, changes or stops a task.

    `register_task(path, helper, user_sid, deadline)` registers it (the `register-desktop` verb's work), on a thread of its own as `run_task` asks, making the `\gate` folder with a protected descriptor (owner Administrators; full access for SYSTEM and Administrators; read for the user's SID), refusing with `SetUpWrong` a folder or task that exists with a weaker owner or DACL, updating a task that passes, and reading it back through the same check; it never deletes, stops or starts a task.
  - `launch.rs`: `Suspended::adopt` (with `AdoptError`), which takes such a child by handle and an `EndReport` (the sink a drop that could not end the child tells, with its pid and the error, since a drop has no caller to return it to), and `Suspended::release` (gives the child up without ending it, as `Released`); `EnvironmentBlock::from_wide`, which checks a received block; `job.rs`: `Job::holds_process`.

It also holds `tools.rs` (the dotnet tool restore and its `<Work>.tools` record), `packages.rs` (the pnpm, bun or npm install before a routed `pnpm`, `bun`, `bunx`, `npm` or `npx` command and its `<Work>.packages` record), `forward.rs` (the pipes forwarded to stdout and stderr, or, for a local run, into its `LogWriter`: the readers that stamp, tag and count a command's lines), `stamping.rs` (which of `box run`'s lines are stamped and which stay bare protocol lines, the box's root line, and `ProcessLines`, the thread that writes the command job's process lines under the output lock), `heartbeat.rs` (the command heartbeat: the job's CPU, and for a `wsl` command the WSL VM's too, on `gate-watchdog`'s `Pump`), `inflight.rs` (the `inflight` verb: which locks under `{Root}\work` a routed run holds) and `stop.rs` (terminating the job).

`msys.rs` is the MSYS keeper, started from `run.rs` after the heartbeat: Git's `cat.exe`, found above the box's `git.exe` and owned by one of `gate_win32::TRUSTED_OWNERS` (Administrators, SYSTEM or TrustedInstaller), kept running in a job of its own so no killed MSYS start-up leaves Git's shared section locked.

It also finds the trusted Git `bin` (`git_bin`), which `run.rs` (`with_git_bin_first`, `with_path_first`) puts first on each command's `PATH` and `preflight.rs` reports when there is none.

`outputs/` is a routed run's outputs, shared by both ends: `glob.rs` (a re-export of `gate-inputs`'s `glob`, the output globs and the exclusions, case-insensitive), `walk.rs` (the Windows walk, with `Found` and `Walked` from `gate-inputs`'s `walk`: the matching files below a folder, skipping links and junctions; `walk_with_refused` also notes the files refused for their names, reading a folder whose name is not plain through a verbatim path to count them), `hash.rs` (SHA-256 of a file; the stream hash, `Hashing` and `sha256_of`, is `gate-inputs`'s `hash`).

Also in it are `manifest.rs` (the manifest's build from a walk while `select`, which picks the files a run changed or the PC lacks, is `gate-inputs`'s `manifest`), `cache.rs` (the PC's hash cache: the hashes of its last built manifest, reused for a file whose size and last write still match).

`archive.rs` holds the Windows side of the `.tar.zst` (the `pack` driver over `gate-inputs`'s `Packer`, with `pack_one` and `check_inside`) and the Windows writer of the archive: `unpack`, `extract_into` and `Unpacking`, the `Place` through which `gate-inputs`'s `archive` reader hands it each member and copy; the reader, its refusals and limits are `gate-inputs`'s.

`stale.rs` names the folders a passing routed build left stale, from a walk of the worktree, the judging globs and the brought-back globs; `run.rs` says the line.

`gate-inputs`'s `names` holds `is_git_s` and `is_lfs_config`, the `.git*` and `.lfsconfig` names that the globs and the sync-back both refuse, and `is_plain_path`, `is_plain_part` and `is_device`, the plain-path rule the globs, the walk, the pack and the archive reader share; `outputs/names.rs` re-exports `is_git_s`, `is_lfs_config` and `is_plain_path` for the Windows box's own callers. The manifest types (`Manifest`, `Held`, `HeldBy`, `MANIFEST_LIMIT`) and `Stamp` are `gate-inputs`'s `manifest`, which `outputs/manifest.rs` and `walk.rs` re-export.

The box packs and sends with it (`boxside/outputs.rs`, GATE-44 part B); the PC's install is `remote/install.rs` (part D). The Rust client builds the manifest, keeps the pending marker, reads the box's outputs line and fetches the archive (`remote/outputs.rs`, parts C1 and C2), then verifies and installs it (`remote/install.rs`).

The client's inputs, which reuse the module's glob matcher, hash cache and archive writer, are built in `remote/inputs.rs`. `gate-wire` holds its payload accessors.

The client's Git LFS part is `remote/lfs.rs`: it lists the snapshot's LFS pointers and the manifest of the objects they name, reads the objects from the worktree's LFS store, packs the ones the box lacks, and makes the diff and put calls (reusing the inputs' request, watch and fallback plumbing).

The box's part is `boxside/lfs.rs`: the `lfs` verb's protected store and install, the run's cover check of the `LfsDigest`, the checkout's `-c` pins and the per-run scratch folder; `boxside/run.rs` applies them to its checkout and back commit.

## Integration Footguns

- **Change a file format** (a field, a type, a file name, an object name) → also change `gate-state`, re-capture its fixtures (`crates/gate-state/tests/state/fixtures/README.md`), raise `v` when an old reader would misread it, update [design.md, Formats](design.md#formats), and send ops-tower a repo inbox request, since it reads every format through a pinned rev of `gate-state`.
- **Add a box step that writes into the work folder before the command runs, or a new skip-if-unchanged record beside it** → the interrupted-command clear (`WorkGit::cleared_interrupted`) must clear it: a file written after the recorded start is removed, but a record beside the folder is removed only by name, so add its suffix to the clear's list (as `.warm`, `.packages` and `.tools` are), or a killed run leaves a record that vouches for a folder the clear emptied.
- **Change a CLI spelling** → also change the compatibility layer in `gate-args`, and every reader of command-line text: ops-tower's activity join and the hooks that inspect a gated command (inventory section 3, "Process-visible facts") match both spellings until the layer goes.
- **Change a stable output line** (STALLED, TIMED OUT, TRANSFER TIMED OUT, BACKSTOP, `waiting for the machine (critical)`, `Full output:`) → it is a breaking change for the scripts in inventory section 3 and the built-in marker regex; prose lines change freely.
- **Write a suite case that runs several gates against one fake-ssh steps file** → give each run its own steps file when any of its calls is watched with a short stall window: a call the watchdog kills before `fake-ssh` logs its verb leaves its step untaken, and every later call then draws the step meant for the one before it.
- **Write a test that starts `gate.exe`** → give it a non-default state root (`--state-dir`): a gate on the default root takes the machine's real slots and writes the real journal, where it fights every session's gates.
- **Change what counts as a WSL command** → `is_wsl_command` (`crates/gate-watchdog`) is used by `watch.rs` for the local W6 rule and by `boxside/run.rs` (`One::wsl`) for the box heartbeat's VM rule; a change to it changes both.
- **Change the cmd.exe word rules** → the gate and `gate box` share them in `gate-args`; a fix in one place is a fix in both, and its test covers both callers.
- **Add a box git step that walks the tree (`--untracked`, `ls-files -o`)** → run it with the tree as its working directory (`WorkGit::quiet_in_tree`, `crates/gate/src/boxside/run.rs`): `--work-tree` does not scope such a walk, and the box's own working directory is the ssh user's profile.
- **Compare a path against git's worktree root** → git names the worktree by its real path from any spelling (a `subst` drive, a junction), so the path goes through `run::resolved` first. The four `is_within` callers are `run.rs`, `no_build.rs`, `remote/client.rs` and `remote/git.rs`.
- **Run a routed command on the builder's desktop** → a desktop run holds a normal remote slot while it waits for the desktop (up to the 60 s `REMOTE_LIMIT`), so other routed runs of the PC can fall back `full` meanwhile, and the wait counts against the client's backstop.
- **Change the slot marker or a kernel object name** → nested gates (`crates/gate/src/nesting.rs::parse` reads the marker, and `nesting/binding.rs` opens the parent's job by the same name to check the marker binds to it), `gate stop-tree` and ops-tower's mutex probe all read names; the root hash rule in [design.md, State root](design.md#state-root) applies to every name.
- **Change how a kill reaches a command's tree** → the escaped-tree kill in `crates/gate/src/escaped.rs` (a `gate run` kill) and the other kill sites (the box's stop, the remote client, `gate push`: GATE-140) must agree on what is ended. The escaped-tree kill spares no build server or shared daemon, since each run's build servers live in its own job (GATE-190).

  The stall check, the cores and the clock already count the escaped tree under the job's members (`escaped::outside_the_job` in each sample), and every kill of a running `gate run` command ends the recorded escaped processes too, whose launcher may have exited.
- **Build the gate or the desktop helper** → the gate's version text comes from `gate-wire` (`build_version`, the package version from `[workspace.package]` plus `GATE_BUILD_ID`; `gate`, `gate-desktop` and `gate-box-unix` all print it), and the helper's `Hello` carries it, for the box to compare with its own.

  Build the helper with the same `GATE_BUILD_ID` as `gate.exe` (`tools/install.ps1` builds both in one `cargo build --release -p gate -p gate-desktop` with one `GATE_BUILD_ID` and installs the helper beside `gate.exe`, replacing the pair together); a helper built without it is `+dev` and matches only another `+dev` build.
- **Ship a new exe, or rename `gate` or `gate-desktop-helper`** → the exe needs its own `cargo:rustc-link-arg-bin=<name>=/DEPENDENTLOADFLAG:0x800` line in its crate's `build.rs` and an `image` test, since a link argument naming a stale bin is ignored silently and the exe would load DLLs from its own folder. A build with `RUSTFLAGS` or `CARGO_ENCODED_RUSTFLAGS` set loses `+crt-static` from `.cargo/config.toml` and is refused.
- **Run a command that waits for its whole job, or read a headless Godot run's log** → Godot's console wrapper waits for every process in its job, so anything that idles there (Roslyn's compiler server, an MSBuild node) holds the command until the stall kill: the gate sets `UseSharedCompilation=false` and `MSBUILDDISABLENODEREUSE=1` on every command for this, and a caller cannot set either. Godot's stdout is also block-buffered on a pipe, so the last line in the log is not where Godot was.
- **Set an ACL on a builder's tool install (the Godot root, a browser folder)** → a deny entry that carries SYNCHRONIZE on an exe makes every launch fail with "Access is denied", which the probe words as `cannot run <exe>: Access is denied.`; on a folder it stops a process without SeBackupPrivilege from listing it, a routed command under the restricted token included. icacls's simple rights `D` and `W` carry SYNCHRONIZE, its specific rights `DE`, `WD`, `AD` and `DC` do not, so deny with `(CI)(DE)`, not `(CI)(D)`.

  On a .NET Godot install, a folder that cannot be entered (`GodotSharp\Api\Debug`) makes every Godot launch, `--headless` included, raise a task-modal ".NET assemblies not found" alert that nobody in session 0 or on a hidden desktop can answer, so the process hangs after its banner while `--version`, which returns before .NET starts, still answers and the probe calls the install healthy.
- **Reproduce a box output reader falling behind** (`boxside/forward.rs`) → suspending the whole box with `NtSuspendProcess` does not reproduce it, since the writer and the readers stop together; suspend the one reader thread instead, found by its name (`forward stdout` or `forward stderr`, read with `GetThreadDescription`), so the command's output arrives while the reader does not read it.
- **Cancel a thread's pending I/O (`CancelSynchronousIo`)** → it waits for its target thread to run, and aimed at a thread still starting on a console it can wait forever, wedging the canceller (the box's drain, whose `HANG_GUARD` cannot fire since the stuck thread checks it). Cancel only a thread that has said it is reading, as `boxside/forward.rs`'s `reading` flag does.
- **Change `gate-state` or `proc-table`'s public API** → ops-tower builds against them by git rev; a breaking change needs its matching change there, by inbox request.

## Test locations

- `crates/gate-state/tests/state/`: every format against its fixtures, claims, counts, the critical and queue views, journal reading. Fixtures in `crates/gate-state/tests/state/fixtures/`.
- Unit tests inside each pure crate (`gate-watchdog`, `gate-args`, `gate-router`, and `gate-state`'s pure parts): run on Windows and on Linux. Quoting round-trips and path rewrites are property tests.
- `crates/gate/tests/`: the black-box suite, a test target with `required-features = ["test-seams"]`. A new behaviour of the binary gets a case here, with its own state root and ordering-only asserts. `suite/install.rs` runs `tools/install.ps1` against a temporary `LOCALAPPDATA` and registry key.
- Run everything through the gate with `cargo nextest run --workspace --all-features --cargo-profile test-release`; the pure crates alone on Linux with `cargo nextest run` (or `cargo test`) on those packages. Which tests a change reaches, as nextest filtersets: [test-map.md](test-map.md).
