# gate — architecture

gate is a Cargo workspace whose `gate` binary (`gate.exe`) queues heavy commands onto a fixed number of CPU slots, watches them and kills runaway process trees. Its layers, bottom up: the shared state crates (`gate-state`, `proc-table`), the pure rule crates (`gate-watchdog`, `gate-args`, `gate-router`), the Win32 layer (`gate-win32`) and the binary that composes them.

The rule that shapes it: every file and kernel object another process sees is defined once, in `gate-state`, and the pure crates hold no Windows types, so they build and test on Linux. The design is [design.md](design.md); terms used in a project sense are in the [glossary](GLOSSARY.md).

`gate-state` and `proc-table` exist (moved in from ops-tower with their history, GATE-4), and so do `gate-args` and the `gate` binary's skeleton (GATE-32).

`gate-win32` exists with the named mutexes and events (GATE-33), and the `gate` binary has the slot loop (GATE-34, GATE-30), `gate stop-tree` (GATE-57) and the box side's `boot` and `preflight` verbs (GATE-59), its `run` and `stop` verbs (GATE-60) and its `outputs` verb (GATE-44 part B). `gate-watchdog` exists as a pure crate (GATE-56), and the `gate` binary uses it through `watch.rs` (GATE-58).

`gate-router` exists as a pure crate (GATE-66): the routing decision, `remote.json` parsing, the `-like` matcher, the path rewrite and the work-folder key. The `gate` binary asks it for the routing decision through `route.rs`.

## Layers

- **`proc-table`** (`crates/proc-table/`): owns the process snapshot model (`ProcessInfo`, `ProcessTable`, `ProcessTree` with its `descendants`) and its Windows reader, plus `command_line_of(pid)`, another process's command line read from its memory. References `windows-sys` in its `win32` module only. Never depends on any gate crate: ops-tower and its other crates use it too.
- **`gate-state`** (`crates/gate-state/`): owns every file format in the state root, their readers and writers, the path and object-name rules, journal history and the dashboard state ops-tower shows. References `proc-table`. Never depends on `gate-win32`, `gate-watchdog`, `gate-router` or the binary, and its API exposes no `windows` or `windows-sys` types.

  It reads two layouts, told apart by `Generation` (`model.rs`; `Generation::detect` looks for `%LOCALAPPDATA%\gate\cutover.flag`, and `StateInputs.generation` carries the answer). `v1.rs` is `gate.exe`'s, under the state root (`counts_path`, `read_counts`).

  `counts.rs`, `claims.rs`, `remote.rs`, `state.rs` and `win32.rs` (`slot_count_path`, `live_inputs`, `dashboard_state`) are what ops-tower uses; the `gate` binary never does. They read the PowerShell gate's layout under `%LOCALAPPDATA%\gate\` until the flag exists and then `gate.exe`'s under `%LOCALAPPDATA%\gate\v1\`, with the waiters taken from its tickets.

  `cutover.rs` is what `gate cutover` writes: `write_cutover_flag` (the flag, holding its write time in RFC 3339 UTC, replacing any flag there) and `copy_slot_counts_to_v1` (the PowerShell gate's counts into the default root's `v1\slot-counts.json`, never replacing a file there; its outcome is `CountsCopy`).

  `drain.rs` is the cutover drain's read-only view of the PowerShell gates still alive: `powershell_gates` lists the heavy, light and remote-slot claims, the critical claim and every ticket, by the dashboard's liveness rule and sorted by `since`, and counts a file it cannot read in `unreadable`.

  `counts.rs` also writes the counts files for ops-tower's Gates tab (`apply_slot_count`, `write_slot_counts`): the PowerShell layout's file, then `gate.exe`'s `v1\slot-counts.json` beside it. `apply_slot_count` keeps the other pool's valid count, replaces a missing, blank, invalid or non-object file, and fails with `ApplyError::Read` on a file that exists but cannot be read, leaving it untouched.
- **`gate-watchdog`** (`crates/gate-watchdog/`, pure): owns the free-share, load-adjusted clock, stall, ceiling and backstop arithmetic over samples (`share.rs`, `watch.rs`, including `measure_cpu` and the progress that build servers and the WSL VM add).

  It also owns the classifiers of build servers, build clients and `wsl` commands over names and command lines (`servers.rs`: `is_build_server`, `is_compiler_server` and `is_compiler_image`, which takes the test seam's image name; with the build servers' priority rule `server_target` and `server_left` over an `Option<PriorityClass>`, `None` being an unreadable class), the kill lines, and the pure formatting of the diagnostics block a kill writes (`diagnostics.rs`: `lines`, `failed_block`, `failed_line` and the caps `JOB_LINES` and `OUTSIDE_LINES`).

  The box heartbeat's beat rule and pump are in `heartbeat.rs`.

  The cores-hint arithmetic is not built yet. References nothing of the gate's but plain data types. Never reads a clock, a process or a file itself: the clock, the samples and the CPU are injected.
- **`gate-args`** (`crates/gate-args/`, pure): owns the gate's own argv (the subcommand CLI and the compatibility layer), C-runtime and cmd.exe quoting, the `%VAR%` refusals and the PATHEXT resolution rules; the command's words are in `cmdline.rs` (C-runtime quoting, `command_text`), `batch.rs` (batch targets, cmd.exe quoting, refusals) and `program.rs` (program resolution). Never depends on `gate-win32`; the environment and file lookups it needs are injected.
- **`gate-router`** (`crates/gate-router/`, pure): owns the routing decision (`decide`, `Route`), `remote.json` parsing (`config.rs`), the `-like` matcher (`like.rs`), the in-worktree path rewrite (`rewrite.rs`), the work-folder key (`key.rs`), over strings; `decide.rs` also drops `--no-build` and pins `SourceRevisionId` on the builder's words.

  Reads no file, runs no git, ssh or process, and has no clock or environment: each fact comes through its `Facts` trait, asked only at the rule that needs it. Never depends on `gate-win32`, `windows-sys` or any other gate crate; its only dependencies are `serde_json` and `sha2`.
- **`gate-win32`** (`crates/gate-win32/`, Windows only).

  Built so far: named mutexes, events and process start times (the gate's own, and `process_start_of(pid)` for another process, `None` for a pid that is gone or exited).

  Also `device_target` (`device.rs`: the target of a drive letter's DOS device over `QueryDosDevice`, which the routing facts use to follow `subst` drives), `system_directory` (the folder holding cmd.exe), `runs_below_normal` (the gate's own priority class), `win32_message`, `boot_time` (when the machine booted), and job objects (`Job`: create, `create_kill_on_close` (a job whose last handle ends its processes, never handed to a piped command), terminate, process ids, `accounting`; `OpenedJob`: open by name with query and terminate access, `open_to_list` with query access only (the priority guard uses it), process ids, terminate).

  Process stopping is `StoppableProcess` (open, created, wait, terminate; in `tree.rs`). `working_set(pid)` (`memory.rs`) is another process's working set in bytes, `None` for a pid that is gone or exited.

  Suspended process creation is `Launch` → `Suspended` → `Running`, whose `Launch.output` is a `LaunchOutput`: `Files { log, err_log }` for the command's output files, or `Piped` for the bridge's pwsh, which has stdin and stdout piped and the gate's own stderr (`Suspended::take_pipes` hands back its `StdioPipes { stdin, stdout }`). Also `EnvironmentBlock`, `same_variable_name` and `PriorityClass`.

  The box's piped launch is `PipedLaunch` → `PipedSuspended` (in `piped.rs`: a `PipedConsole` that is hidden or attached to the caller's, breakaway from the caller's job, two pipes and a query-only job handle inherited), with `check_plain_file` and `breakaway_refused`. Also in `piped.rs`, for the bridge's reads of a pipe: `cancel_pending_io(&File)` (cancels a read another thread has pending) and `cancelled(&io::Error)` (whether an error is that cancel).

  `PipedLaunch::start_suspended_within_fed` (in `piped.rs`) is the same suspended start in a job with stdin piped as well, a `PipedFed` holding the write end, which `gate push` feeds the exe through.

  `console.rs` is the box's UTF-8 console: a `Donor` (a `cmd.exe` put in the command's job) and `Utf8Console`, which attaches the process to the donor's console, sets the code pages, and returns through a keeper. `event.rs`'s `NamedEvent` also gives the named manual-reset event of a job's stop signal (`create_new_manual` by the run, `open_to_set` by `stop`).

  Both launches create the process through the shared `create.rs` (`check_launch`, `startup_info`, `AttributeList`, `create_process`, `create_inheriting`), so the refusals before the call and the startup information are one code path.

  The spawn lock (in `create.rs`) is held while the layer starts any process: `create_inheriting` makes inheritable copies of a launch's handles under it, so the gate's own handles are never inheritable, and `spawn(&mut Command)` starts a std `Command` under the same lock. A std spawn anywhere in the gate goes through `gate_win32::spawn`.

  `priority.rs` is another process's priority class: `Priority`, `priority_of(pid)` and `set_priority(pid, priority)`, `None` for a pid that is gone and an error for a class that cannot be read (`priority_of` asks for `PROCESS_QUERY_INFORMATION`); the gate takes that error as an unknown class.

  Also the samples in `times.rs` (`system_times`, `process_times`, `file_time_now`) and the Ctrl+C handler in `interrupt.rs` (`Interrupt`: install, is_raised, raise; `Running::wait_or_interrupt` and `NamedEvent::wait_or_interrupt` end a wait early; `Interrupt::presses()` counts the presses, and `Running::wait_or_interrupt_again` ends a wait on a press after the one already seen, the bridge's second Ctrl+C).

  Owns job objects, process creation, named mutexes and events, priority, console handling and taking samples. References `proc-table` and `windows-sys`. Never holds policy: what to kill and when is `gate-watchdog`'s.
- **`gate`** (`crates/gate/`, Windows only): the binary. Owns the subcommands, the wait loop, the run, the journal writes, the remote pool and client call of a routed run (the client of a production gate is the `remote.ps1` bridge in `remote/bridge.rs`; the Rust client in `remote/{client,payload,retry,syncback,transport,watchdog}.rs`, with the snapshot and git runner beside it, exists in test-seams builds only, except the transport's ssh words and `Ssh::find`, which `gate push` uses) and `gate box`. References every crate above. Nothing depends on it.

  Its modules so far: `route.rs` (the routing facts read from the routing file, git and the drive table, and the lines of the decision), `remote/` (`mod.rs` holds the `RemoteClient` a routed run calls, its call and outcome, and the scripted client of the `test-seams` build, and a client that cannot start makes a routed run fall back with reason `client`; `bridge.rs` is the bridge to `remote.ps1`: it checks its parts, starts pwsh on the shim in the gate's job, sends the request on pwsh's stdin and reads the answer as control lines on its stdout; `git.rs` is the git runner shared with `route.rs`; `snapshot.rs` is the snapshot and the bridge commit of the Rust remote client, reached only by `--test-remote-snapshot`; `syncback.rs` is the client's sync-back, which fetches the builder's back ref and applies it to the worktree; `watchdog.rs` is the client's pure rules for when a call is killed, its kill line, the watchdog's tick, the stall window and the 64 KiB line cap; `client.rs` runs the calls in anonymous kill-on-close jobs and holds the watch, the stop and Ctrl+C).

  Beside them are `slots.rs` (`ThisGate`, the gate's identity built once and shared with the journal; the pool, liveness, take, claim, wake and deletes), `wait.rs` (the wait loop and its lines, the barrier of a critical request ahead, the reserved light slots beside it, the lend of a light parent's slot and the writing of the pause marker, over `Waiter`, the wake event, ticket, sleep and heartbeat that `Wait` and the critical `MachineWait` share), `acquire.rs` (`try_slot` and the abandoned-take line) and `journal.rs` (`RunJournal`, the run's journal lines).

  `machine.rs` is a critical gate's wait for the machine: the critical mutex, the drain, the take of every heavy and unreserved light slot, its lines, the snapshot its `take` journals and the release.

  `pause.rs` is the pause marker: the writer a waiting gate under a parent's slot refreshes on each pass of its wait, and the reader (`PauseReader`, over `live_child_pause_with`) the watchdog in `watch.rs` calls on each sample.

  `stop_tree.rs` is `gate stop-tree`: the snapshot, the tree, the gate jobs and the deepest-first terminates.

  `cutover.rs` is `gate cutover`: the counts copy, the flag write and the drain over `gate-state`'s `powershell_gates`, with its lines, the confirmation window and the Ctrl+C stop.

  `push.rs` is `gate push`: it reads the builders from the routing file (`read_remote_json`, `Config::builders`) and the installed exe, then makes one ssh call per builder through `transport.rs`'s `ssh_words` and `Ssh::find` (the only production use of the transport so far), feeding the exe as base64 on stdin to an embedded PowerShell script, and maps the script's `gate-push: ` lines to the `push: ` lines.

  Also `run.rs` (the run lifecycle: program, batch refusal, queue, take, launch, wait, verdict, release), `log.rs` (the log, its tail and the failure markers), `environment.rs` (the command's environment and slot marker) and `nesting.rs` (the slot marker a gate was started under: its parse, the parent's liveness, and the covered, refused or own-slot decision).

  And `watch.rs` (the watch of a running command: the sampler, the pause read, the load-adjusted clock, the stall kill and the Ctrl+C stop), `servers.rs` (the build servers outside the job and the build client inside it, read once per sample) and `priority.rs` (the per-watch `Prioritizer` that lowers or raises the classified build servers, and `OtherGates`, the guard it reads, at most once a pass and only when a server to move asks, from the tickets, claims and other gates' jobs).

`boxside/` is `gate box`: `mod.rs` (the verbs and their exits), `payload.rs` (the base64 JSON payload), `preflight.rs` (the bare repo, the work folder and the report lines), `boot.rs` (the boot-time line), `run.rs` (the lock, the git flags, the sync, the command, the back commit and the call to pack outputs), `outputs.rs` (the PC's manifest read, the old-archive prune, the pack of a run's outputs and the `outputs` verb that sends and deletes the archive), `tools.rs` (the dotnet tool restore and its `<Work>.tools` record), `forward.rs` (the pipes forwarded to stdout and stderr), `heartbeat.rs` (the command heartbeat: the job's and the build servers' CPU on `gate-watchdog`'s `Pump`) and `stop.rs` (terminating the job).

`outputs/` is a routed run's outputs, shared by both ends: `glob.rs` (the output globs and the exclusions, case-insensitive), `walk.rs` (the matching files below a folder, skipping links and junctions), `hash.rs` (SHA-256 and `is_lower_hex`), `manifest.rs` (the PC's manifest and `select`, which picks the files a run changed or the PC lacks) and `archive.rs` (`pack` and `unpack` of the `.tar.zst`, with strict refusals and limits).

The box packs and sends with it (`boxside/outputs.rs`, GATE-44 part B); the PC's fetch and install are not built yet (parts C-D). `boxside/payload.rs` holds its payload accessors.

## Integration Footguns

- **Change a file format** (a field, a type, a file name, an object name) → also change `gate-state`, re-capture its fixtures (`crates/gate-state/tests/state/fixtures/README.md`), raise `v` when an old reader would misread it, update [design.md, Formats](design.md#formats), and send ops-tower a repo inbox request, since it reads every format through a pinned rev of `gate-state`.
- **Change a CLI spelling** → also change the compatibility layer in `gate-args`, and every reader of command-line text: ops-tower's activity join and the hooks that inspect a gated command (inventory section 3, "Process-visible facts") match both spellings until the layer goes.
- **Change a stable output line** (STALLED, TIMED OUT, BACKSTOP, `waiting for the machine (critical)`, `Full output:`) → it is a breaking change for the scripts in inventory section 3 and the built-in marker regex; prose lines change freely.
- **Write a test that starts `gate.exe`** → give it a non-default state root (`--state-dir`): a gate on the default root takes the machine's real slots and writes the real journal, where it fights every session's gates.
- **Change the cmd.exe word rules** → the gate and `gate box` share them in `gate-args`; a fix in one place is a fix in both, and its test covers both callers.
- **Change the slot marker or a kernel object name** → nested gates (`crates/gate/src/nesting.rs::parse` reads the marker), `gate stop-tree` and ops-tower's mutex probe all read names; the root hash rule in [design.md, State root](design.md#state-root) applies to every name.
- **Change `gate-state` or `proc-table`'s public API** → ops-tower builds against them by git rev; a breaking change needs its matching change there, by inbox request.

## Test locations

- `crates/gate-state/tests/state/`: every format against its fixtures, claims, counts, the critical and queue views, journal reading. Fixtures in `crates/gate-state/tests/state/fixtures/`.
- Unit tests inside each pure crate (`gate-watchdog`, `gate-args`, `gate-router`, and `gate-state`'s pure parts): run on Windows and on Linux. Quoting round-trips and path rewrites are property tests.
- `crates/gate/tests/`: the black-box suite, a test target with `required-features = ["test-seams"]`. A new behaviour of the binary gets a case here, with its own state root and ordering-only asserts. `suite/install.rs` runs `tools/install.ps1` against a temporary `LOCALAPPDATA` and registry key.
- Run everything through the gate with `cargo test --workspace --profile test-release --all-features`; the pure crates alone on Linux with `cargo test` on those packages.
